# The E7 measurements, C1 to C10

The harness for the export, deletion, register and mail measurements C1 to C10. **These are
measurement scripts, not gates.** `scripts/check.sh` does not run them, nothing here asserts a
bound, and every number is recorded with the seed that produced it, the machine's load average at
the time and the exact command. The rule for the directory is "none a claim until measured": a
measurement that asserted a target would turn a number into a promise.

## What is measured, and where each number lands

| Id | Script | What it measures |
|---|---|---|
| C1 | `c1-c3-export.mjs` | the copy script on case 25a's fixture and on a plan-figure company: duration, peak RSS (sampled from outside the child), document bytes |
| C2 | `c1-c3-export.mjs` | the same export with a concurrent writer in another company, and that writer's own worst latency |
| C3 | `c1-c3-export.mjs` | the SHA-256 and the completeness check, each timed standalone over the same document |
| C4 | `c4-c6-deletion.mjs` | the row count at which `api.delete_company` exceeds `app_server`'s 8 s statement timeout, through the route |
| C5 | `c4-c6-deletion.mjs` | the same sizes through `scripts/delete-company.mjs`, with the lock's hold time as a waiter sees it |
| C6 | `c4-c6-deletion.mjs` | the deletion at 500,000 rows, which is `app.limit_delete_rows()` exactly |
| C8 | `c8-register.mjs` | `register.mjs verify` at 10,000 lines, and the sync's full read of an epoch with its query plan |
| C9 | `c9-c10-latency.mjs` | 25 invitations against the local catcher, against the same 25 in `handover` |
| C10 | `c9-c10-latency.mjs` | the alert path with a sink that never answers, against `alert()`'s 1.5 s bound |
| C4, supporting | `c4-role-settings-probe.mjs` | whether the local PostgREST applies `app_server`'s `lock_timeout` and `statement_timeout` to an impersonated request at all, without which C4 cannot see an edge |
| C8, supporting | `c8-append-cost.mjs` | where the register sync spends its time: the cost of appending n lines, at three sizes, against a file under the system temporary directory and no stack |

C7, the local restore rehearsal's duration, is **not here**: `tests/e7/stack/restore.test.mjs` is
the rehearsal. Two recorded runs took 43,145 ms and 43,278 ms.

Each script writes one JSON record per measurement to `evidence/e7-docs-repro/measurements/`, appends
a line to `index.txt` there, and prints it. `evidence/` is excluded by `.gitignore`, so the records
stay on the machine that made them.

## Running them

Each script reseeds through `bash tests/db/00-seed.sh` at its start, runs **alone**, and leaves the
database dirty. Reseed between them:

```
node tests/e7/measure/c1-c3-export.mjs   --label <label>   # leaves a ~250 MB company
bash tests/db/00-seed.sh
node tests/e7/measure/c4-c6-deletion.mjs --label <label>   # leaves half a million rows
bash tests/db/00-seed.sh
node tests/e7/measure/c8-register.mjs    --label <label>   # leaves 100,000 audit rows
bash tests/db/00-seed.sh
node tests/e7/measure/c9-c10-latency.mjs --label <label>
bash tests/db/00-seed.sh
```

`--label` decides every generated byte of every fixture, so the same label on the same seed
reproduces the same fixture, and the label is what each record carries as its seed. Nothing here
calls `supabase stop`, `start` or `db reset`, and nothing runs while another stack suite runs.

## The fixtures, and their one honest limit

`seed.mjs` builds three:

- **`plan-figure`**: C1's second company, at the project's planned capacity figures. 50 agents, ten candidate
  versions each at 262,144 bytes, 300 releases with assembled content near 393,216 bytes, 25 active
  and 25 removed memberships beside the first administrator, and a 10,000-row download ledger.
- **`sized --rows N`**: a company whose deletion row total is exactly N, padded with audit rows,
  which is what `tests/db/30-deletion.sh` case 25b already pads with.
- **`case-25a`**: the oversized company, through `tests/db/e7-lib.sh`'s own
  `build_oversized_company`, so this harness and probe 30 raise the same fixture from one body of
  code.

**The limit, written where it cannot be missed.** The candidate rows are inserted with the product's
own identity trigger **enabled**, so each is a row the identity rule accepted. The envelope and
release rows are not: their **identity** triggers are disabled for the bulk insert and the derived
columns are computed in the fixture. Their **immutability** trigger is NOT disabled: `releases_one_current`
allows one current release per agent and target, so each agent's earlier releases are superseded by
the published-to-published update that trigger already admits, which is the product's own transition. So the releases are of the right size and number and are **not**
proof that the product's assembly rules hold at this size; the route suites under `tests/e4/` to
`tests/e6/` prove those, one release at a time. What the measurements then measure is the export's
streaming, the deletion's duration and the lock's hold, and nothing more.
